# Сайт Stay на своём сервере (VPS)

Один и тот же код работает и на Vercel, и на своём сервере. Куда собирать, решает сборка:
на Vercel (есть переменная `VERCEL`) — адаптер Vercel, иначе — обычный Node-сервер (`STAY_TARGET=node`).

## Что на сервере работает иначе, чем на Vercel

| Что | Vercel | Свой сервер |
|---|---|---|
| Запуск | функции Vercel | `node dist/server/entry.mjs` под pm2 (1 процесс) |
| Настройки из админки (главная, SEO, объекты, ИИ-помощник, счётчики) | Vercel Blob | JSON-файлы в `STAY_DATA_DIR` (`src/lib/store.ts`) |
| Сжатие картинок | `/_vercel/image` | `/img` (sharp, кэш на диске, `src/pages/img.ts`); оригиналы с чужих сайтов сохраняются в `STAY_DATA_DIR/media-src` |
| Кэш страниц, 10 минут | CDN Vercel, сброс по тегам | в памяти процесса, сброс тем же `purge()` (`src/lib/pageCache.ts`) |
| Ночной сброс кэша 03:00 | Vercel Cron | cron пользователя `stay` |
| Выкладка | пуш в GitHub | пуш в `main` → GitHub Actions → SSH → `deploy/deploy.sh` |
| HTTPS | Vercel | nginx + бесплатный сертификат Let's Encrypt (certbot) |
| Вход в админку | один пароль `ADMIN_PASSWORD` | пользователи с ролями в базе SQLite, код на почту, защита от подбора, журнал |

## Сервер

Ubuntu 24.04, 2 ядра, 4 ГБ памяти, 40 ГБ диска. Сборка идёт на самом сервере, ей нужно около 1,5 ГБ памяти.

## Первый запуск

1. Зайти на сервер под root и выполнить:
   ```
   curl -fsSLO https://raw.githubusercontent.com/<владелец>/<репозиторий>/main/deploy/setup-server.sh
   bash setup-server.sh git@github.com:<владелец>/<репозиторий>.git
   ```
   Для приватного репозитория скрипт покажет ключ сервера: его нужно добавить в GitHub → репозиторий → Settings → Deploy keys (только чтение) и запустить скрипт ещё раз. Скрипт для приватного репозитория можно передать на сервер и как файл.
2. Заполнить `/home/stay/stay.env` по образцу `deploy/stay.env.example`: пароль админки, секреты, домены.
3. Собрать и запустить: `sudo -u stay bash /home/stay/app/deploy/deploy.sh`.
4. Направить домен на IP сервера (A-запись), потом выпустить SSL: `certbot --nginx -d stay.com.tr -d www.stay.com.tr`.

## Админка: пользователи и вход

База — файл `/home/stay/data/admin.db` (SQLite, встроен в Node, отдельный сервер базы не нужен). В ней пользователи, сессии, коды входа, попытки входа и журнал.

- Первый вход: логин `admin` и пароль из `ADMIN_PASSWORD` — так создаётся владелец. Потом он добавляет остальных в разделе «Пользователи».
- Роли: владелец (всё + пользователи и журнал), администратор (все разделы), редактор (главная и объекты), SEO (только SEO).
- Пароли хранятся как хэш scrypt, от 10 символов, буквы и цифры. Сессия — 12 часов, её токен в базе тоже хэшем.
- Если настроена почта (`SMTP_*`) и у пользователя указан адрес, после пароля приходит 6-значный код (10 минут, 5 попыток).
- 5 неверных паролей на логин или 20 с одного адреса за 15 минут — вход блокируется на 15 минут.
- Отключение пользователя или смена роли сразу закрывает его входы.
- Резервная копия: `sqlite3 /home/stay/data/admin.db ".backup /home/stay/backup/admin-$(date +%F).db"` (или просто копировать папку `data` по cron).

## Автовыкладка из GitHub

Сайт собирается в GitHub Actions (на сервере мало памяти для сборки), на сервер уходит только готовый архив
(`.github/workflows/deploy-vps.yml` → `deploy/ssh-gate.sh` → `deploy/release.sh`). Скрипт выкладки подменяет версию,
проверяет `/ru/`, при сбое сам возвращает прежнюю (вместе с зависимостями), прогревает кэш, хранит 3 последних архива.

Настройка один раз:
1. На своём компьютере создать ключ только для выкладки: `ssh-keygen -t ed25519 -f stay-deploy -N "" -C github-deploy`.
2. На сервере (под root):
   ```
   install -d -o stay -g stay -m 700 /home/stay/bin /home/stay/.ssh /home/stay/releases
   install -o stay -g stay -m 755 /home/stay/app/deploy/ssh-gate.sh /home/stay/bin/ssh-gate.sh
   echo 'command="/home/stay/bin/ssh-gate.sh",no-port-forwarding,no-X11-forwarding,no-agent-forwarding,no-pty <содержимое stay-deploy.pub>' >> /home/stay/.ssh/authorized_keys
   chown stay:stay /home/stay/.ssh/authorized_keys && chmod 600 /home/stay/.ssh/authorized_keys
   ```
   С таким ключом можно только передать архив и выложить его: ни оболочки, ни других команд.
3. В репозитории, Settings → Secrets and variables → Actions:
   - секреты: `VPS_HOST` (IP сервера), `VPS_SSH_KEY` (содержимое файла `stay-deploy`),
     `VPS_KNOWN_HOSTS` (вывод `ssh-keyscan -t ed25519 <IP>` — отпечаток сервера);
   - переменные: `VPS_DEPLOY_BRANCH` — ветка, пуш в которую выкладывает сайт; `STAY_NOINDEX` — `1`/`0`
     (закрыт/открыт для поисковиков, по умолчанию `1`); при необходимости `STAY_API_BASE`, `STAY_CONTENT_API`, `STAY_DOMAINS`.
4. Файл `stay-deploy` после этого удалить с компьютера.

Пока секретов или `VPS_DEPLOY_BRANCH` нет, выкладка пропускается. Вручную — Actions → Deploy to VPS → Run workflow.
`deploy/deploy.sh` (сборка на самом сервере) оставлен как запасной ручной способ: ему нужно ~1,5 ГБ свободной памяти.

## Защита админки

- Пароли — хэш scrypt, от 10 символов, буквы и цифры; сессия 12 часов; 5 неверных паролей на логин или 20 с адреса за 15 минут — блокировка.
- Вход только с кодом из письма — у всех, включая владельца (`ADMIN_REQUIRE_CODE`, по умолчанию включено; нужна почта `SMTP_*`
  и e-mail у каждого пользователя). Аварийно выключить: `ADMIN_REQUIRE_CODE=0` в `stay.env` и перезапуск сайта.
- Вход только по почте. «Забыли пароль?» — ссылка на почту (30 минут, одноразовая), после смены все входы закрываются.
- Первый владелец входит почтой из `ADMIN_EMAIL` и паролем из `ADMIN_PASSWORD`, код приходит на эту почту; затем он обязан задать свой пароль. После сброса пароля владельцем
  пользователь тоже задаёт свой при входе. До этого разделы админки и их API закрыты.
- Смена своего пароля закрывает все другие входы этого пользователя.
- `ADMIN_ALLOW_IPS` — админка открывается только с перечисленных адресов (остальным 404).
- `/admin` и `/api/admin` — только по HTTPS, не кэшируются, не встраиваются в чужие страницы, закрыты от поисковиков.

## Перенос настроек с Vercel

Настройки из админки (главная, SEO, отметки объектов) лежат в Vercel Blob. Перед переездом их можно скачать
и положить в `/home/stay/data/config/` с теми же именами файлов: `home.json`, `seo.json`, `objects.json`.
Ключ ИИ-помощника заново ввести в /admin: на сервере он шифруется другим секретом (`STAY_SECRET`).

## Объекты из Portfolio (без dev.stayproperty.com)

Раньше объекты на продажу и в аренду сайт брал у dev.stayproperty.com. Теперь их можно брать прямо из Portfolio API:

1. В `stay.env` заполнить `STAY_PORTFOLIO_USER`, `STAY_PORTFOLIO_PASSWORD`, `STAY_PORTFOLIO_TOKEN` (пользователь с ролью API User в админке Portfolio).
2. Пробный запуск, ничего не меняет, показывает первую карточку:
   `cd /home/stay/app && sudo -u stay node --env-file=/home/stay/stay.env scripts/portfolio-sync.mjs --limit=20`
3. Первый полный запуск (около 1700 объектов, 7 запросов на объект — порядка 10–20 минут):
   `sudo -u stay node --env-file=/home/stay/stay.env scripts/portfolio-sync.mjs --full`
   Снимок ложится в `STAY_DATA_DIR/portfolio/` (`sale.json`, `rental.json`, `objects/<id>.json`, `meta.json`).
4. Cron (ставит `setup-server.sh`): каждые 30 минут — только изменённые объекты, в 04:00 — все заново. Лог: `/home/stay/logs/portfolio-sync.log`.
5. Пока `STAY_OBJECTS_SOURCE=auto`, сайт берёт объекты из снимка, если он есть, а иначе с dev. Когда снимок проверен,
   поставить `STAY_OBJECTS_SOURCE=portfolio` и перезапустить сайт: тогда к dev за объектами сайт не ходит вообще.

Защита: если пришло меньше половины объектов от прошлого снимка, снимок не заменяется. При сбое отдельного объекта остаётся его прошлая версия.
Через dev пока остаются стройки и квартиры из Битрикс24 (`/api/projects`, `source=bitrix`), страницы ЖК, меню и блоки главной: при закрытии dev они берутся из встроенной копии.

## Картинки

- Свои картинки лежат в `public/media` (перенесены со старого stay.com.tr скриптом `node scripts/import-media.mjs`, ужаты до 1920 px).
  Сайт отдаёт их уменьшенными копиями (320–1920 px, AVIF/WebP) через `/img` на своём сервере и `/_vercel/image` на Vercel.
- Фото с чужих сайтов (объекты, новости с dev.stayproperty.com и т. д.) при первом показе сохраняются в `STAY_DATA_DIR/media-src`,
  дальше берутся с диска. Готовые уменьшенные копии — в `STAY_DATA_DIR/img-cache`.
- API dev.stayproperty.com пока отдаёт часть картинок с адресов `https://stay.com.tr/upload/...` и `/local/...`. После переключения
  домена на новый сайт эти пути должен отдавать nginx из папки старого сайта (или из её копии), пока картинки не переедут.

## Полезное

- Логи: `sudo -u stay pm2 logs stay-site`
- Перезапуск: `sudo -u stay pm2 reload stay-site`
- Проверить кэш страницы: заголовок `x-stay-cache` (MISS — собрана сейчас, HIT — из кэша, STALE — старая копия при сбое API).
